# CLAUDE.md

## Project

Morgonlistan — a morning/evening checklist app for kids. Plain vanilla HTML/CSS/JS on the frontend: no build tools, no frameworks, no bundler. This is deliberate — keep it this way unless there's a strong reason to change. Data is backed by Supabase (Postgres + Auth), added after real usage showed local-only storage couldn't support one family across multiple devices, or multiple separate families.

## Files

- `index.html` — shell; loads `style.css`, the Supabase JS client, `config.js`, and `app.js`
- `style.css` — all styling
- `app.js` — all application logic (auth, state, rendering, interactions)
- `config.js` — **gitignored**, holds this machine's Supabase URL + anon key; copy `config.example.js` to create it
- `config.example.js` — committed template for `config.js`
- `supabase/schema.sql` — the database schema (`families` table, RLS policies, auto-create-row trigger); run once per Supabase project via the SQL Editor
- `supabase/email-templates/` — every auth email shares one layout: `_layout.html` (icon, fonts, colours, footer) plus `build.py`, which fills in each email's own words/action and writes the paste-ready `confirm-signup.html` / `reset-password.html` (pure ASCII, entities for å/ä/ö — a locale-less shell once garbled them via `pbcopy`). Edit those two, run `python3 supabase/email-templates/build.py`, then paste the output into the Supabase dashboard (Authentication → Email Templates) by hand, same pattern as the Edge Function below. A new email is one entry in `TEMPLATES`. `email-logo.png` in the repo root (a 192px copy of the app icon, served by GitHub Pages) is what the emails' header image points at
- `serve.py` — local dev server
- `.claude/launch.json` — dev server config for the Browser pane preview tool
- `brand-guide.md` — the settled visual identity and copy tonality reference (see `ROADMAP.md` §4); supersedes the removed `morgonlistan-brand-spec.md`
- `app-icon.svg` — source of the App Store icon; see "Icons" in `brand-guide.md` for how it maps to `ios/App/App/Assets.xcassets/AppIcon.appiconset/AppIcon-512@2x.png`
- `ios/` — the native iOS wrapper (Capacitor); see "Native iOS app" below
- `www/` — **gitignored**, a generated copy of the four web files for Capacitor to bundle; never edit directly, see "Native iOS app"
- `capacitor.config.json`, `package.json` — Capacitor/npm config, added solely to support the iOS wrapper (see "Native iOS app")

## Running locally

1. Create a Supabase project, run `supabase/schema.sql` in its SQL Editor, then copy `config.example.js` to `config.js` and fill in that project's URL + anon key (Project Settings → API).
2. ```bash
   python3 serve.py 8000
   ```

Always use `serve.py`, not `python3 -m http.server` — the plain stdlib server sends no cache-control headers, which caused stale-JS bugs on mobile Safari reloads. `serve.py` sends `Cache-Control: no-store` on every response.

Then open `http://<mac-lan-ip>:8000` on a phone on the same WiFi (find the IP with `ipconfig getifaddr en0`).

## Auth & data model

Signing in is email + password via Supabase Auth (`renderLoginScreen()` in `app.js`, with `login`/`signup`/`forgot` modes drawn on one shared screen). "Glömt lösenordet?" (forgot password) is its own dedicated email-only mode rather than reusing the login form, matching the standard pattern of not making someone fill in a password field they don't have. Password recovery is detected synchronously from `window.location.hash` at script load (`type=recovery`) rather than relying on Supabase's `PASSWORD_RECOVERY` event, which doesn't reliably fire when a session already exists on the device — see the comment above `inPasswordRecovery` in `app.js`. Each signed-in family gets exactly one row in the `families` table, auto-created by a Postgres trigger the moment they first sign up (`supabase/schema.sql`). Row Level Security means a user can only ever read/write their own row.

**Email sending**: auth emails (signup confirmation, password reset) go out via custom SMTP (Supabase Project Settings → Authentication → SMTP Settings), not Supabase's shared default sender — that shared sender has a low rate limit that was hit during our own testing. Configured with **Resend**, sending from the verified domain `morninglist.app` (DKIM via a `resend._domainkey` TXT record, DMARC via `_dmarc` TXT, plus `rsend`/`send` CNAMEs pointing at Resend's sending infrastructure). If email deliverability ever breaks, check Resend's dashboard and that domain's DNS records first. Both auth emails use custom branded templates (see "Files" above for how they're built and deployed). Signup confirmation is an 8-digit code typed into the app (`renderSignupConfirmScreen()`), with the emailed link as a fallback that lands on an "account activated" page in browsers, because a link can't be relied on to open the app rather than a browser.

The whole app state lives in that row's single `state` jsonb column — same shape as the old localStorage blob, which kept the migration mostly to "swap the read/write layer," not a redesign:

```
{
  kids: [{ id, name, color }],
  tasks: [{ id, name, emoji }],         // morning list
  eveningTasks: [{ id, name, emoji }],  // evening list
  rewardPerSession: number,             // currency earned per fully-completed session
  currencySymbol: string,               // emoji or text, e.g. "🍬"
  completions: [{ kidId, taskId, date, amount, timestamp }],
  settledWeeks: { [kidId]: weekStartMs },  // last week's reward a parent confirmed as handed out
  resetSchedule: [{ effectiveAt: ms, day: 0-6 }],  // which weekday the reward week ends on, from when (default Saturday)
  reminders: { enabled, morning: "07:00", evening: "19:00" },  // daily reminder notifications, iPhone app only
  setupDone: boolean,  // the first-run wizard was completed or skipped
  endWeekEarlyOnMorningDone: boolean,  // per kid: end their week the moment morning is done on the reset day
  earlyWeekEnds: { [kidId]: { closedCycleStart, endedAt, nextRegularBoundary } },  // most recent early end only
}
```

`completions` is one flat log used for three things, distinguished by `taskId`:
- a real task's id — just tracks that task as checked today (`amount: 0`, no currency)
- `"session-reward-morning"` / `"session-reward-evening"` — the currency earned for finishing a whole session
- `"manual-adjustment"` — a parent's manual balance tweak in Parent Mode

`timestamp` is used for precise weekly-boundary math; older records without it fall back to noon of `date`.

**Offline resilience**: `saveState()` stashes the change in `localStorage` (`PENDING_SAVE_KEY`) before writing, retries with backoff (3 attempts) on failure, and leaves the change cached if all retries fail. A pending change is flushed automatically on the next app load (`bootstrapApp`) and as soon as the browser reports connectivity again (`window`'s `online` event) — a dropped connection mid-use no longer silently loses a kid's progress. If reopening the app while still offline, the cached pending state is shown directly rather than an outdated (or empty) fetch.

**Shared family access**: today, "sharing" a family (e.g. both parents) means literally sharing one login email — there's no concept of multiple auth users linked to one family row yet. That's a deliberate v1 simplification (see `ROADMAP.md` if a proper multi-user-per-family model is ever needed).

**Account deletion** (Parent mode → Konto → Radera konto, `openDeleteAccountModal()` in `app.js`): requires typing "RADERA" to confirm, then calls the `delete-account` Edge Function (`supabase/functions/delete-account/index.ts`). That function deletes the `auth.users` row via the Admin API using the service role key (only available server-side); the `families` row disappears automatically via its `on delete cascade` FK — no separate data-deletion step needed. Added to satisfy Apple App Store Guideline 5.1.1(v) (apps with account creation must offer in-app account deletion, not just a support contact). Deploy/update this function via the Supabase dashboard's Edge Functions editor (no CLI installed on this machine) — paste the file's contents in as a new function named `delete-account`.

## Key architectural decisions

- **No frameworks, no build step, by design** — matches the user's preference for something simple to inspect and edit without heavy tooling.
- **Morning/evening switching**: `getCurrentPeriod()` returns evening for hours 18:00–03:59, morning otherwise. This drives which task list shows, each kid's panel color (a deliberately darker shade of their own color at night, not a generic dark mode), and the sun/moon icon in the title.
- **Reward model**: 1 currency unit is earned per fully-completed session, not per task (see `toggleTask()`). This caps the total at 2/day, 14/week by design — that cap is load-bearing for the jar display below, not arbitrary.
- **Weekly reset**: the reward week ends on a day *and time* a parent sets in Parent mode (Inställningar → Veckan slutar) — Saturday 18:00 by default, matching EVENING_START_HOUR since that's when the evening list used to flip over, but the two are independent settings now (changing one doesn't move the other). Stored as `state.resetSchedule` = `[{ effectiveAt, day, hour, minute }]`: changing either field via `setResetSchedule(partial, now)` appends an entry effective at the end of the week in progress, so no week is ever cut short and no reward moves or is lost — only the transition week can be shorter/longer (an extreme case: changing just the time, on the reset day itself, produces a transition "week" as short as the time difference). `setResetSchedule` builds the new entry from whatever's already *pending* if a change is already staged, not from what's currently active, so changing day and time as two separate steps combines them instead of the second overwriting the first; ending up back at exactly what's active now cancels the pending change. `getRewardWeekStart` / `getNextRewardWeekEnd` / `getPreviousRewardWeekStart` all take an optional `(now, schedule)` and use calendar days, not 7×24h, so a DST change can't move a boundary off its configured time. Verified: the default schedule matches the old Saturday-18:00 algorithm on 5,000 random moments; every weekday change; a time-only change combined with a later day-only change (and the reverse); the exact cutoff second on both sides of a transition, including the pathological same-day time-change case; reward attribution across a transition; DST. The kid card header shows `weekDaysLeftText()` ("3 dagar kvar", "slutar i kväll").
- **Color system** (see `brand-guide.md`): kids pick one of 12 curated muted base colors (`KID_COLORS`); `deriveKidTheme()` derives the done-state background tint from that same hue via HSL math (`hexToRgb` / `rgbToHsl` / `hslToRgb` / `rgbToHex`). The checkmark and celebration accents are deliberately *not* derived — they're the shared `SPLASH_COLORS` (`tick` for a checked task, `reward` for a completed session), designed to work against every base color at once. Don't add a third kind of accent color without adding it to `SPLASH_COLORS` and the brand guide — the whole point is one small, shared set of "win" colors, not per-feature hardcoding.
- **App-wide chrome** (login screen, primary buttons, modal sheets, general background — everything outside a kid's own card) also follows the brand: the global background and `.modal-sheet` are the warm paper cream (`#F7F2E9`), and `.primary-btn` / focus rings / selected states use Coral Pop (`#F0654A`, same as `SPLASH_COLORS.reward` and the email CTA button) rather than the old blue theme. Secondary "add" buttons (`.add-row-btn`, `.stepper-btn`) use a calm sand tint, not a color from the splash set — they shouldn't visually compete with the one real call to action on a screen.
- **Reminders default to on** (`DEFAULT_REMINDERS.enabled`) for a new family, but iOS still needs an explicit ask — `drawReminders()` proactively calls `ensureReminderPermission()` once, the first time the section renders with `enabled: true` and permission still "prompt" (real iOS never returns "prompt" a second time once answered, so this can't turn into repeated nagging). An existing family's own saved `reminders.enabled` — including an explicit `false` — is never overwritten by this default; only an account with no `reminders` key at all gets it, which is indistinguishable from "never configured this."
- **Reset defaults to Saturday 12:00**, not 18:00 — deliberately decoupled from `EVENING_START_HOUR`, chosen so the week wraps up around when a Saturday morning routine would be finishing rather than at the evening switch.
- **End week early on morning done** (opt-in, Parent mode → Sluta tidigt): a kid can end their own week the moment their morning list is finished on the reset day, instead of waiting for Klockslag. Independent per kid — one kid finishing doesn't affect a sibling still working through their list — via `kidWeekStart()` / `kidWeekEnd()`, which sit alongside the plain family-wide `getRewardWeekStart()` / `getNextRewardWeekEnd()` and are used wherever a *specific kid's own* balance/summary is meant (`weeklyBalance`, `pendingWeekSummary`, `weekDaysLeftText(kidId)`); the plain family-wide functions are untouched and still drive `weekHistory()`, the week-end notification, and anywhere no single kid is meant. Recorded once in `state.earlyWeekEnds[kidId]`, using the family's own *unadjusted* values captured at the moment it fires (`closedCycleStart` / `nextRegularBoundary`), not recomputed live — an earlier version compared against a live-recomputed family boundary and silently stopped applying the moment the family's own checkpoint passed later the same day, caught by testing that exact case. Self-limiting to one transition: once "now" reaches `nextRegularBoundary`, the kid is back on the shared family schedule until they trigger early again. `maybeEndWeekEarly()` is called from `toggleTask()`'s existing "just completed the whole session" branch (already fires once per day) and guards against the reset day's own Klockslag fallback having already fired earlier today by comparing calendar dates — comparing against `getNextRewardWeekEnd(now)` directly can never work, since that's always `>= now` by construction, a second bug caught by testing. `weekHistory()` deliberately keeps using the plain family-wide boundaries even for a kid with an early end, as an accepted simplification: the two moments are always the same day, and nothing happens between finishing morning and a same-day fallback, so the numeric difference is normally zero.
- **Password reset confirmation**: the same problem as signup's link — a reset link usually opens somewhere other than the app it was requested from, and bootstrapping the full working app right there just invites using that instead of switching to the native app. `renderSetNewPasswordScreen()` now shows `showPasswordResetDoneScreen()` ("Lösenordet är sparat — gå tillbaka till appen") on the web, with the same "Fortsätt på webben istället" escape hatch as the signup version, and only bootstraps directly when `isNativeApp`. Unlike signup, there's no way to sign the original app in automatically here — that app never sees the new password chosen elsewhere — so the copy asks for a manual return rather than claiming it happens on its own.
- **Web landing page**: a first-time, signed-out *web* visitor sees `showLandingScreen()` (what it is, three steps, Skapa konto / Logga in) instead of the bare login form. It's part of `app.js`, not a separate page, so no URL, redirect allow-list, Universal Link or email link had to move. Never shown in the native app (`isNativeApp`), never when an auth link just landed (`pendingAuthError`), and only until the visitor has clicked through once on this browser (`VISITED_KEY` in localStorage, set by `showLoginScreen()`). The onboarding screens sit in a centered 420px column so wide web windows don't stretch them.
- **First-run wizard**: a family with no kids and `setupDone` false gets `renderOnboarding()` — how many children (1–6), then their names on one screen with a colour each (spread around the hue wheel by `evenlySpacedKidColors()`; tap the dot to change), then everything is created at once in a single `saveState()`. Nothing is saved before the last step, so quitting halfway just starts over. Default task lists, currency and the weekly cycle are already in `defaultState()`, so the app works the moment it's done and Parent mode is only for changing things. "Hoppa över" marks setup done and opens Parent mode; a family with `setupDone` but no kids (skipped, or all removed later) sees the plain `renderNoKidsScreen()` instead, never the wizard again. `normalizeState` sets `setupDone` true for any existing family that already has kids.
- **Week-end notification**: a third scheduled notification (id 1003, `REMINDER_IDS.weekEnd`) fires once at the next reset moment (`getNextRewardWeekEnd()`), not daily — deliberately generic text ("Veckan är slut! Dags att dela ut veckans belöning.") since a scheduled notification's content is fixed at scheduling time and can't show a live count. Controlled by the same Påminnelser on/off toggle as the daily reminders and rescheduled the same way, so it keeps pointing at the correct next boundary even across a reset-day change.
- **Week history** (Parent mode → Tidigare veckor): `weekHistory()` walks backward from the current week using the same boundary math as the rest of §1, listing the last 8 *completed* weeks (never the one in progress) with each kid's total. Correct across a reset-day change (the transition week shows at its own, possibly shorter/longer, length) and a DST shift.
- **Daily reminders**
 (iPhone app only): local notifications via `@capacitor/local-notifications` — iOS holds and delivers them, so they arrive with the app closed or force-quit, no server involved. Times are family-wide in `state.reminders` (default 07:00 / 19:00, off until a parent turns them on in Parent mode → Påminnelser); the permission is per device, and iOS is only asked when a parent switches them on. `syncReminders()` cancels ids 1001/1002 and reschedules to match the settings; it runs after the family's data loads and after every change, and `cancelReminders()` runs on sign-out. The plugin is reached as `Capacitor.Plugins.LocalNotifications` (no bundler); on the web it's absent, so the Parent mode section isn't shown. The notification text is fixed at scheduling time — it can't include live numbers ("3 candies so far").
- **Logo lockup**: every onboarding/auth screen opens with `brandLockupHTML()` (inline sun icon, then "Morgonlistan" as a small label in one fixed spot) followed by a heading that is the screen's own title — never the app name. The spacing rules (36px clear space, 12px icon→name, 36px name→heading, 16/32/24/40 below) are in `brand-guide.md` §7 and are shared by the emails; change both together.
- **Typography**: Fraunces (display/serif, loaded in `index.html`) for anything that's the brand speaking — the app title, kid names, dialog titles (see `.home-title` / `.kid-name` / `.modal-title` / `.parent-header .title` in `style.css`). Karla (the global body font) for everything the product itself is doing, including uppercase section labels — never switch a `.section-title`-style label to Fraunces, that's a Karla-only role per the brand guide.
- **End of the week**: at the Saturday 18:00 reset the jar empties and the reward is gone (no carry-over), but each kid's card first shows "Förra veckan: N 🍬" with an "Utdelat" button (`pendingWeekSummary()`, `buildWeekSummary()`), so the reset never looks like lost data. Tapping it goes through the parental gate (`openParentGate(onPass)`) and records the week in `state.settledWeeks`. Only the week that just ended is ever shown; nothing shows when nothing was earned. Tested at the exact cutoff second and across a DST change (the previous week's start is computed in calendar days, not by subtracting 7×24h). Reset day is still fixed at Saturday — see ROADMAP §1.
- **Reward jar display**: a fixed 7×2 grid of 14 slots (`buildRewardJar()`), filled vs. faint outline, at a fixed pixel height regardless of count — deliberate, to avoid layout shift/flicker as the count changes. A balance above 14 (from a manual adjustment) shows a completely full jar plus a small "+N" badge rather than ever resizing the jar.
- **Parental gate**: a birth-year check (`openParentGate()`), not a simple confirm button — must compute to age 18–100. No example year in the placeholder, since a kid could just copy it.

## Native iOS app

Wrapped with **Capacitor** (`app.morninglist.ios`, display name "The Morning List") — the one deliberate exception to "no build tools," scoped narrowly to just the native app packaging. The actual web app (`index.html`/`style.css`/`app.js`/`config.js`) is still zero-build and still what GitHub Pages serves directly; nothing about the live web app changed.

Capacitor requires its bundled web assets in their own folder (`www/`), not the repo root, so **after editing any of the four web files, run `npm run cap:sync`** before testing/building the iOS app — this copies the current files into `www/` and syncs Capacitor's `ios/App/App/public`. This is the one place a "build step" exists, and it only matters for the native app; the live website needs no such step and keeps working exactly as before.

Requires Node.js (installed via `nvm`, not Homebrew — this machine had neither) and full Xcode (not just Command Line Tools) to open/build/run. Uses Capacitor 8's default Swift Package Manager integration, **not CocoaPods** — this machine's system Ruby (2.6) is too old for modern CocoaPods, but that's a non-issue since no Podfile is generated.

To open the Xcode project: `npx cap open ios`.

**Universal Links**: the password-reset email link (`https://morninglist.app/...`) opens the native app directly instead of Safari, via `.well-known/apple-app-site-association` (served from the repo root, so GitHub Pages hosts it — no server config needed) plus the `com.apple.developer.associated-domains` entitlement in `ios/App/App/App.entitlements`. That entitlement needs both the App ID's Associated Domains capability enabled in the Apple Developer portal *and* a provisioning profile generated after that capability was added — an older profile predating it will fail the archive step with a clear "doesn't include the Associated Domains capability" error. `App.entitlements` is wired into the build via `CODE_SIGN_ENTITLEMENTS` in `project.pbxproj` (both Debug and Release configs). On the JS side, Capacitor's `@capacitor/app` plugin surfaces the incoming URL via the `appUrlOpen` event (app already running/backgrounded) or `getLaunchUrl()` (cold launch) — see the top of `initAuth()`'s section in `app.js`; both paths just set `window.location.hash` and reload, reusing the same synchronous `type=recovery` detection as the web flow rather than a separate code path.
